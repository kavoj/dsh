# Agent Note: 随星业务菜单作为通用侧栏数据

Status: implemented

[English](2026-09-18-suixing-sidebar-catalog.md) | 中文

## 问题

随星发行需要在侧栏提供两个可折叠的业务菜单——AI 参谋部（辅助名称 Agent 中心）与自动化工厂（辅助名称 WorkFlow 中心）——并具备折叠记忆、最近使用条数上限、搜索、“查看全部”入口，以及明确的加载、空、离线、错误状态。把这些菜单写进侧栏外壳，等于把业务名称与业务条目塞进基础布局，之后每加一个菜单、换一个发行方都要改外壳代码。已批准的原型还为每个能力固定了一份页面定义——主引导、用途说明、快速任务与资料提示——如果菜单本身就是展示代码，这些内容无处安放。

## 决策

侧栏新增一个面向注册方的目录服务（`ctx.sidebarCatalog`）与一个通用区域，由随星发行向其发布内容。

外壳只负责通用部分：折叠状态、五行的最近使用上限、分组内搜索、查看全部跳转、条目派发，以及四种加载呈现。分组以数据形式到达——id、顺序、标题、可选辅助名称、条目、可选主面板键——标题与标签由注册方完成本地化。任何业务名称都不会进入外壳。服务上报 `claimed`，因此未发布任何目录的发行不会渲染区域，也不会渲染外层元素，默认侧栏 DOM 保持不变；释放最后一个注册（或卸载插件）即回到该状态，这也是 `claimed` 随其持有者一起释放、而不是一次性锁存的原因。

目录条目放在主面板 slot 的注入面里，而不是钩子里：注册方的载荷对一次注册而言是静态的。外壳用服务自身的 `useCatalog` 选择器驱动区域，渲染器则按与其他注入面相同的方式绑定该载荷。目录模板是一个组件服务所有菜单，分组通过注册的 `inject: () => ({ group })` 送达，因此第二个菜单是一次注册而不是一个页面。随星的两个菜单来自 `directory/specs.ts`，其中每个条目的键由能力 id 计算得出，字典缺键会变成编译错误，而不是页面上的一行空白。

## 备选方案

**把两个菜单直接写进侧栏外壳。** 外壳将持有随星文案与条目，下一个菜单又是一次外壳改动。方案禁止把所有条目硬编码进基础布局。

**把菜单做成 `sidebar.panellist` 条目。** 该 slot 是外壳自己的全局面板列表：一个面板一行，没有折叠、最近使用、搜索或分组状态。要满足这些交互，就得给共享列表加能力，等于替所有人改动默认侧栏。

**把每个菜单的字典与接线都塞进品牌包的单一命名空间。** 两件事的生命周期不同：品牌只占用一次且不再变化，而目录会成批发布与释放。分开的命名空间让目录可以被单独释放而不影响品牌，也为第三个菜单留出位置。

**现在就为每个能力建一个主面板。** 十三项能力十三个面板，正是方案 §6.3 模板化决策所否定的“一能力一页面”。在能力自己的页面出现之前，其条目打开所属菜单的目录；改指向只需改一处 `target`。

## 后果

`ui-sidebar` 增加一个服务、一个区域组件及其样式，以及两个测试套件（折叠与注册表行为、区域的状态与搜索与派发）；该包维持逐文件 100% 覆盖率，未发布状态由面板列表与指针滚动两条基准测试固定，默认侧栏 DOM 因此不会回退。

`ui-brand-suixing` 增加能力元数据、目录模板与已发布菜单，其 `apply()` 现在也需要 `sidebarCatalog`。菜单只在 `suixing` 构建 profile 下出现，并且包内测试挂载真实 slot 管线，证明菜单的面板键确实服务于其目录页。两份字典承载原型原文；字典与元数据互相校验。

品牌名称在同一轮里也移到了本包的 `suixing-brand` 命名空间：客户端 UI i18n 门禁拒绝展示代码中的字面量，而专有名词应当放在拥有它的字典里。

能力条目当前打开所属菜单的目录，因此一次点击到达的是定义而不是可用页面：这是方案“先定义”的边界，不是已完成的闭环。内容创作工具与项目列表尚未发布。四种加载状态由区域自身的测试覆盖；真实平台加载及其重试路径随后续平台闭环任务一起到来，运行时 `reportStatus` 调用也在那时才存在。
